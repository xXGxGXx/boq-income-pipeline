### 1. Gitleaks 8.0

- **Source:** [Gitleaks v8.0.0 release notes](https://github.com/gitleaks/gitleaks/releases/tag/v8.0.0) (published 2021-11-22) and the [v8.0.0 announcement issue](https://github.com/gitleaks/gitleaks/issues/683).
- **Finding:** Gitleaks v8.0.0 is a breaking rewrite focused on secret detection. It replaced `go-git` with shelling out to `git log -p` and `git diff`, added `detect`, `protect`, `help`, and `version` commands, added multiline rules and richer finding metadata (`StartLine`, `EndLine`, `StartColumn`, `EndColumn`, `RuleID`), added a default config path of `(--source/-s)/.gitleaks.toml`, added 60+ rules, and routed log messages to stderr with verbose findings on stdout. It removed cloning, `repo-config`, files-at-commit support, and dedicated commit options, replacing commit controls with `--log-opts` (any `git log` options).
- **How it changed a decision:** **unverified – source needed.** A search of the Handover Protocol docs (including TURN-LOG-v4, MERGE-LOG-v5, STATE-v5) and of this repository found no Gitleaks config, workflow step, or recorded decision to adopt or reject it. Current secret scanning in this repo is `scripts/privacy_scan.py` via `.github/workflows/checks.yml`. What would verify a decision: a commit, workflow change, or protocol note that names Gitleaks.

### 2. GitHub squash-merge API

- **Source:** [GitHub REST API: Merge a pull request](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request). Related Drive fact: [TURN-LOG-v4](https://docs.google.com/document/d/[redacted]/edit?usp=drivesdk) records “PR 12 merged (privacy_scan payout exclusion, squash 1ecb9f4)”.
- **Finding:** A pull request can be squash-merged through `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge` with body parameter `merge_method` set to `squash` (also allowed: `merge`, `rebase`). Optional body fields include `commit_title`, `commit_message`, and `sha` (the head SHA that must match). A successful merge returns 200 with `sha`, `merged`, and `message`. 405 means the merge cannot be performed. Official docs also say: “We recommend using the asynchronous merge API instead. This endpoint does not support stacked pull requests or merging with a merge queue.”
- **How it changed a decision:** **Partially verified.** TURN-LOG-v4 documents that PR 12 was squash-merged as commit `1ecb9f4`. That confirms squash merge was used for that PR. No source was found that records a standing rule to always use this REST endpoint (versus the GitHub UI, `gh`, or `merge-async`). What would fully verify a standing API decision: a protocol or AGENTS.md rule naming this endpoint.

### 3. Auto-delete head branches

- **Source:** [Managing the automatic deletion of branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches) and [Update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository) (`delete_branch_on_merge`).
- **Finding:** Repositories can automatically delete a pull request’s head branch after the PR is merged. The setting is labelled “Automatically delete head branches” under Settings → General → Pull Requests. The REST field is `delete_branch_on_merge` on `PATCH /repos/{owner}/{repo}`; it defaults to `false`. Branch protection rules and repository rulesets can prevent automatic deletion. For a pull request opened from a fork, GitHub uses the setting on the fork (the head repository), and the user merging the pull request must have write access to the fork, or the branch is not deleted automatically.
- **How it changed a decision:** **unverified – source needed.** No Handover Protocol or repository file was found that records enabling or disabling this setting. What would verify it: the repository’s `delete_branch_on_merge` value, or a protocol note of the choice.

### 4. Drive 100-version rollover

- **Source:** [Google Drive API: Manage file revisions](https://developers.google.com/workspace/drive/api/guides/manage-revisions) (last updated 2026-09-03 UTC) and [Check activity & file versions](https://support.google.com/drive/answer/2409045).
- **Finding:** For blob files (uploaded non-Google files), revisions that are not the head revision and are not marked “Keep Forever” are purgeable. Google’s API guide says purgeable revisions are typically preserved for 30 days, but can be purged earlier if a file has 100 revisions that are not designated “Keep Forever” and a new revision is uploaded. Up to 200 revisions can be set to “Keep Forever” (`keepForever` on the revisions resource; Drive API v2 used `pinned`). The head revision is never auto-purged. Google’s Help page states a version might be permanently deleted after 30 days or if there are 100 newer versions, unless “Keep forever” is set. This automatic purge applies to blob file revisions, not to separately named Google Docs (the protocol’s TURN-LOG-v4 / MERGE-LOG-v5 style). The revisions list API may also be incomplete for frequently edited Google Docs, Sheets, and Slides.
- **How it changed a decision:** **unverified – source needed.** AUTO-SYNC and the protocol’s practice of creating new versioned filenames (for example TURN-LOG-v4) is documented, but no source was found that chose that pattern *because of* the 100-revision purge. What would verify it: a protocol or AUTO-SYNC note that cites this limit.

### 5. Antigravity one-retry rule

- **Finding:** In the article’s SDK loop example, `max_retries=1` “limits each section: the first attempt plus one fix. - **How it changed a decision:** **unverified – source needed.** No Handover Protocol or repository file was found that adopts this exact one-retry cap. MAXIMUM-EFFORT / anti-regression rules about not repeating a failed approach are a different, broader rule and should not be treated as the same finding. What would verify it: a skill or protocol rule that cites `max_retries=1` or “one retry then hand to a human.”

### 7. OWASP allowlist format

- **Source:** [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html).
- **Finding:** OWASP recommends defining what the application accepts and rejecting values outside those rules (allowlist), rather than trying to recognise every malicious string (denylist). Field-level rules in the cheat sheet are: fixed choices require exact membership in the allowed set; numbers and dates require expected type, accepted format, and minimum and maximum values; strings require length limits and the characters or structure required by the field; objects require allowed fields, required fields, and rules for missing or null values; arrays require minimum and maximum item counts and validation of every item, including nested objects. For JSON, required and additional properties must be configured explicitly; listing a property alone neither requires it nor rejects unknown fields. Regular expressions should match the entire value (for example Python `fullmatch`), with input length bounded before matching. Allowlisting is not a substitute for parameterized queries or context-aware output encoding.
- **How it changed a decision:** **unverified – source needed.** No Handover Protocol or repository file was found that records adopting this allowlist format for a specific interface. What would verify it: a schema, validator, or protocol note that cites this cheat sheet.

### 8. CI fetch-depth 0

- **Source:** [actions/checkout README](https://github.com/actions/checkout/blob/main/README.md): “Only a single commit is fetched by default, for the ref/SHA that triggered the workflow. Set `fetch-depth: 0` to fetch all history for all branches and tags.” Current workflow: `.github/workflows/checks.yml` at commit `b7efe9a2692fdc0d4b858d44c672f56721832ae5`.

This repository’s `checks.yml` uses `actions/checkout@v5` in every job and does not set `fetch-depth`, so CI currently gets the default single-commit checkout.
- **How it changed a decision:** **unverified – source needed.** The workflow has not been changed to `fetch-depth: 0`. No protocol note was found deciding to keep or change the default. What would verify a decision: a workflow edit or a written choice to stay shallow.

## Four merge-queue findings

### 9. `merge_group` event requirement

- **Source:** [Managing a merge queue](https://docs.github.com/en/pull-requests/collaborating-with-issues-and-pull-requests/using-the-merge-queue) and [Events that trigger workflows: `merge_group`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group). Current workflow: `.github/workflows/checks.yml`.
- **Finding:** If a merge queue is used and required checks are GitHub Actions jobs, workflows must also trigger on the `merge_group` event. Official docs: “If your repository uses GitHub Actions to perform required checks on pull requests in your repository, you need to update the workflows to include the `merge_group` event as an additional trigger. Otherwise, status checks will not be triggered when you add a pull request to a merge queue. The merge will fail as the required status check will not be reported. The `merge_group` event is separate from the `pull_request` and `push` events.” A minimal example is:

  ```yaml
  on:
    pull_request:
    merge_group:
  ```

  The documented activity type is `checks_requested`. This repository’s `checks.yml` currently triggers on `push` (branch `main`), `pull_request`, and `workflow_dispatch` only; it does not include `merge_group`.
- **How it changed a decision:** **unverified – source needed** as a completed change. The finding is that `merge_group` is required *if* a merge queue with Actions required checks is enabled, and that this workflow does not yet declare it. No source was found that the repository has enabled a merge queue. What would verify a decision: a `merge_group` trigger added to `checks.yml`, or a written decision not to use a merge queue.

### 10. Squash-merge PUT endpoint (and merge-queue limitation)

- **Source:** [GitHub REST API: Merge a pull request](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request) and [Merge a pull request asynchronously](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously).
- **Finding:** The squash-merge REST call is `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge` with `merge_method=squash`. Official docs state that this (synchronous) endpoint “does not support stacked pull requests or merging with a merge queue,” and recommend the asynchronous merge API instead: `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge-async`. An asynchronous request can merge in the background or add the pull request to a merge queue; a 202 response includes a UUID used to fetch the result.
- **How it changed a decision:** **unverified – source needed** for a standing merge-queue policy. TURN-LOG-v4 records a squash merge of PR 12, which is consistent with using squash as a merge method, but does not record use of a merge queue or of `merge-async`. What would verify it: a protocol rule or automation that calls `merge-async` when a merge queue is required, and uses the synchronous PUT only when no queue is in play.

### 11. Workflow dispatch POST endpoint

- **Source:** [GitHub REST API: Create a workflow dispatch event](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event). Current workflow: `.github/workflows/checks.yml` (`on.workflow_dispatch` is already present).
- **Finding:** A workflow that declares `on: workflow_dispatch` can be started with `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches`. `workflow_id` may be the numeric id or the workflow file name (for example `checks.yml`). The request body requires `ref` (branch or tag name) and may include `inputs` matching inputs declared in the workflow file (maximum 25 properties). Official docs describe a 200 response that includes `workflow_run_id`, `run_url`, and `html_url`.
- **How it changed a decision:** **Partially verified.** `checks.yml` already lists `workflow_dispatch`, so a dispatch POST against this workflow is supported by the file as it stands. No source was found that records a decision to use this POST as the standard way to re-run checks. What would fully verify that policy: a protocol or operator note naming this endpoint.

### 12. Auto-merge polling

- **Source:** [Automatically merging a pull request](https://docs.github.com/en/pull-requests/collaborating-with-issues-and-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request); [Check if a pull request has been merged](https://docs.github.com/en/rest/pulls/pulls#check-if-a-pull-request-has-been-merged); and the merge-async result docs on the same REST page, which say an “enqueued” result “does not mean the pull request has merged” and that eventual status is obtained by checking whether the pull request has been merged.
- **Finding:** Auto-merge merges a pull request automatically after required reviews and status checks pass; it must first be enabled for the repository (with a documented exception: on a branch that requires a merge queue, “Merge when ready” can enable auto-merge even if the repository setting does not allow it). To observe whether a pull request has actually landed, the official check is `GET /repos/{owner}/{repo}/pulls/{pull_number}/merge`: HTTP 204 means it has been merged; HTTP 404 means it has not; the response body is empty. The same check is what official docs point to after an asynchronous merge-queue enqueue, because an “enqueued” `merge-async` result is final for that request and does not later flip to “merged.” No official document was found that specifies a required poll interval or client-side retry loop; only the status check itself is specified.
- **How it changed a decision:** **unverified – source needed.** No Handover Protocol or repository automation was found that enables auto-merge and then polls this endpoint. What would verify it: operator notes or a script that enables auto-merge and then calls `GET .../pulls/{pull_number}/merge` until 204.
